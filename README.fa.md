# race.py — ابزار تست Race Condition

یک ابزار سبک و کم‌وابستگی برای تست **race condition** در HTTP، که چند ریکوست خام را
طوری می‌فرستد که (تا حد ممکن) در یک لحظه به سرور برسند.

دو تکنیکِ تحقیقِ PortSwigger را پیاده‌سازی می‌کند:

- **HTTP/2 single-packet attack** — دقیق‌ترین روش. همه‌ی ریکوست‌ها از قبل بارگذاری می‌شوند،
  بعد «فریمِ آخرِ» هر استریم نگه داشته می‌شود و همه با هم در **یک بسته‌ی TCP** شلیک می‌شوند؛
  در نتیجه سرور همه را تقریباً هم‌زمان تکمیل می‌کند. جیتر شبکه عملاً حذف می‌شود و
  اندازه/تعداد ریکوست دیگر مهم نیست.
- **HTTP/1.1 last-byte sync** — فال‌بکِ خودکار وقتی سرور HTTP/2 ندارد. هر ریکوست کانکشن
  جدا دارد، همه به‌جز بایت آخر را می‌فرستند، پشت یک Barrier صبر می‌کنند، بعد بایت آخرِ همه
  با هم شلیک می‌شود.

> ⚠️ **فقط استفاده‌ی مجاز.** این ابزار را فقط روی سیستم‌هایی به کار ببر که مالک‌شان هستی
> یا اجازه‌ی صریحِ تست داری (مثل اسکوپِ bug bounty یا یک لبِ آموزشی). مسئولیتِ استفاده با توست.

## پیش‌نیازها

- Python نسخه‌ی ۳٫۸ به بالا
- برای موتور HTTP/2: کتابخانه‌ی [`h2`](https://pypi.org/project/h2/)

```bash
pip install h2
```

موتور HTTP/1.1 به هیچ پکیجِ جانبی نیاز ندارد.

## شروع سریع

ریکوست خام را بگیر (در Burp: راست‌کلیک → **Copy to file**، یا متنِ خام را در یک فایل `.txt`
پیست کن). فایل باید از خطِ اولِ درخواست شروع شود، مثل `POST /login HTTP/1.1`.

**۱) یک ریکوست را چندین بار هم‌زمان بفرست** (ریسِ کلاسیک روی یک اندپوینت — دورزدنِ محدودیت،
double-spend، استفاده‌ی دوباره از کوپن و ...):

```bash
python race.py --tls --repeat 30 request.txt
```

**۲) بروت‌فورسِ قالبی / ریسِ چندمقداری** — به‌ازای هر کلمه‌ی wordlist یک ریکوست، همه با یک
session و یک CSRF مشترک:

```bash
python race.py --tls --wordlist wordlist.txt --prime /login examples/login.tmpl
```

**۳) چند ریکوستِ متفاوت با هم** (مثلاً ریسِ چندمرحله‌ایِ وابسته به state):

```bash
python race.py --tls req_a.txt req_b.txt req_c.txt
```

## چطور کار می‌کند

موتور به‌صورت پیش‌فرض `auto` است:

۱. یک کانکشنِ TLS باز می‌کند و با ALPN سعی می‌کند HTTP/2 مذاکره کند.
۲. اگر سرور **h2** داشته باشد، **single-packet attack** را اجرا می‌کند.
۳. وگرنه به موتورِ **HTTP/1.1 last-byte-sync** فال‌بک می‌کند.

با `--engine http2` یا `--engine http1` می‌توانی یکی را اجبار کنی. موتور HTTP/2 به `--tls` نیاز دارد.

### ترتیبِ single-packet attack

۱. **گرم‌کردن (warm-up)** — preface و SETTINGSِ HTTP/2 فرستاده می‌شود و منتظرِ SETTINGSِ سرور
   می‌ماند، تا هندشیک **قبل از** بسته‌ی حساس‌به‌زمان کامل باشد.
۲. **ارسالِ حجم اصلی (bulk)** — برای هر ریکوست، هدرها و همه‌ی بدنه به‌جز بایتِ آخر فرستاده
   می‌شود (اشکالی ندارد چند پکت شود).
۳. **شلیک** — فقط فریم‌های آخرِ نگه‌داشته‌شده‌ی همه‌ی استریم‌ها در یک `sendall()` واحد
   خالی می‌شوند. همین بسته‌ی آخر است که ریکوست‌ها را هم‌زمان می‌کند.

`--gap` (پیش‌فرض `0.10` ثانیه) فاصله‌ی بینِ ارسالِ حجم اصلی و شلیکِ نهایی است.

## قالب‌گذاری (Templating)

همراهِ `--wordlist` و/یا `--prime` استفاده می‌شود. Placeholderها در فایلِ قالب:

| Placeholder   | جایگزین با                                                |
|---------------|-----------------------------------------------------------|
| `§§`          | هر کلمه‌ی wordlist (با `--marker` قابل تغییر است)          |
| `{{SESSION}}` | مقدارِ کوکیِ session که `--prime` می‌گیرد                  |
| `{{CSRF}}`    | توکنِ CSRF که `--prime` می‌گیرد                            |

در حالتِ wordlist مقدارِ `Content-Length` خودکار اصلاح می‌شود (چون طول بدنه با هر کلمه فرق
می‌کند). برای یک فایلِ تکیِ غیرقالبی، اگر بدنه‌اش را دستی عوض کردی `--fix-cl` را اضافه کن.

### `--prime` (گرفتنِ خودکارِ session و CSRF)

خیلی از اندپوینت‌ها به یک **کوکیِ session + توکنِ CSRFِ تازه و منطبق** نیاز دارند. `--prime PATH`
اول یک `GET PATH` می‌زند، هر دو را استخراج می‌کند و در قالب تزریق می‌کند تا همه‌ی ریکوست‌های
موازی از یک جفتِ معتبرِ یکسان استفاده کنند:

```bash
python race.py --tls --wordlist wordlist.txt \
  --prime /login --cookie-name session --csrf-field csrf \
  examples/login.tmpl
```

- `--cookie-name` — نامِ کوکیِ session که از `Set-Cookie` خوانده می‌شود (پیش‌فرض `session`).
- `--csrf-field`  — نامِ فیلدِ فرم که توکن از آن خوانده می‌شود (پیش‌فرض `csrf`).

اگر تارگتت CSRF ندارد، فقط `{{CSRF}}` را از قالب حذف کن؛ اگر کوکیِ خاصی برایت مهم نیست،
`{{SESSION}}` را حذف کن.

## نمونه‌ی قالب

فایلِ `examples/login.tmpl` (مقدارِ `Host`، مسیر، username و نامِ فیلدها را برای تارگتِ خودت
ویرایش کن):

```
POST /login HTTP/1.1
Host: TARGET-HOST
Cookie: session={{SESSION}}
Content-Type: application/x-www-form-urlencoded
Content-Length: 0

csrf={{CSRF}}&username=admin&password=§§
```

## خواندنِ خروجی

هر ریکوست status، طولِ بدنه‌ی پاسخ و زمانِ سپری‌شده را چاپ می‌کند. بعد پاسخ‌ها بر اساسِ
`(status, length)` گروه‌بندی می‌شوند:

```
[*] Results:
  [  0] 123456          -> 200   len=4105  (511.2 ms)
  ...
  [  9] hunter2         -> 302   len=0     (511.2 ms)
  ...

[*] Responses are NOT uniform (likely a race winner / outlier):
    status=302 len=0    -> 1 request(s): [hunter2]
    status=400 len=20   -> 3 request(s): [...]
    status=200 len=4105 -> 14 request(s): [...]
```

معمولاً **گروهِ استثنا (outlier)** همان چیزِ جالب است — مثلاً یک `302` در میانِ انبوهی از
`200`های «ناموفق» یعنی آن ریکوست موفق شده.

برای این‌که واقعاً **ببینی چی فرستادی و چی گرفتی**، فلگِ **`-v` / `--verbose`** را اضافه کن:
برای هر آیتم، دقیقاً ریکوستِ ارسال‌شده و پاسخِ کامل (خطِ status، هدرها و body) را چاپ می‌کند.
سریع‌ترین راه برای فهمیدنِ یک نتیجه‌ی گیج‌کننده است — مثلاً این‌که چرا همه‌ی ریکوست‌ها `400`
برگشتند. خروجی تا `--max-body` بایت برای هر ریکوست/پاسخ بریده می‌شود (پیش‌فرض `2048`؛ برای
دیدنِ کاملِ body مقدارِ `--max-body 0` را بده). یا با `--save-responses DIR` بدنه‌ی همه‌ی
پاسخ‌ها را روی دیسک ذخیره کن.

```bash
python race.py --tls -v --max-body 500 req1.txt req2.txt
```

## همه‌ی گزینه‌ها

| گزینه                 | توضیح                                                                 |
|-----------------------|----------------------------------------------------------------------|
| `files`               | یک یا چند فایلِ ریکوستِ خام. با `--wordlist`، دقیقاً یک فایلِ قالب.    |
| `--host HOST`         | هاستِ مقصد (پیش‌فرض از هدرِ `Host:` فایلِ اول).                        |
| `--port PORT`         | پورتِ مقصد (پیش‌فرض `443` با `--tls`، وگرنه `80`).                    |
| `--tls`               | استفاده از TLS/HTTPS. برای موتور HTTP/2 لازم است.                    |
| `--repeat N`          | هر فایل را `N` بار هم‌زمان بفرست.                                     |
| `--engine`            | `auto` (پیش‌فرض)، `http2`، یا `http1`.                                |
| `--sync`              | حالتِ HTTP/1.1: `last-byte` (پیش‌فرض) یا `connect`.                   |
| `--gap SECONDS`       | فاصله‌ی بینِ ارسالِ حجم اصلی و شلیکِ نهایی در HTTP/2 (پیش‌فرض `0.10`). |
| `--fix-cl`            | اصلاحِ `Content-Length` (با `--wordlist` خودکار روشن است).            |
| `--wordlist FILE`     | به‌ازای هر کلمه یک ریکوست از یک فایلِ قالب بساز.                       |
| `--marker STR`        | نشانه‌ی جای‌گذاریِ wordlist (پیش‌فرض `§§`).                           |
| `--prime PATH`        | اول `GET PATH` بزن؛ `{{SESSION}}` / `{{CSRF}}` را تزریق کن.           |
| `--cookie-name NAME`  | نامِ کوکیِ session برای `--prime` (پیش‌فرض `session`).                |
| `--csrf-field NAME`   | نامِ فیلدِ CSRF برای `--prime` (پیش‌فرض `csrf`).                      |
| `--save-responses DIR`| بدنه‌ی هر پاسخ را در `DIR` بنویس.                                     |
| `-v`, `--verbose`     | ریکوستِ ارسالی و پاسخِ کامل (status/هدر/body) را چاپ کن.              |
| `--max-body N`        | حداکثر بایتِ چاپ‌شده با `-v` (`0` = کامل؛ پیش‌فرض `2048`).            |
| `--timeout SECONDS`   | تایم‌اوتِ سوکت (پیش‌فرض `10`).                                        |

## نکته‌ها و تله‌ها

- **session/CSRF باید تازه و منطبق باشند.** ترجیحاً از `--prime` استفاده کن تا هر اجرا یک
  جفتِ معتبرِ نو بگیرد. اگر آن‌ها را در فایل هاردکد می‌کنی، هر بار ریکوستِ *تازه* بگیر —
  خیلی اپلیکیشن‌ها بعد از یک عملیاتِ موفق کوکیِ session را می‌چرخانند.
- **هر ریسی به مقادیرِ زیاد نیاز ندارد.** برای باگ‌های «یک‌چیز-را-دوبار»، همان یک ریکوست با
  `--repeat 2` (یا بیشتر) معمولاً کافی است.
- **HTTP/2 تنگ‌ترین پنجره را می‌دهد.** اگر تارگت فقط HTTP/1.1 دارد، موتورِ last-byte هم کار
  می‌کند ولی جیترِ بیشتری دارد؛ چند بار اجرا کن.
- **`--gap` را تنظیم کن** اگر سرور در بافرکردنِ حجم اصلی قبل از بسته‌ی نهایی کند است.
- ابزار عمداً حداکثر ۲۵۶ کیلوبایت از بدنه‌ی پاسخِ HTTP/1.1 را می‌خواند.
- **Git Bash روی ویندوز** آرگومانی که با اسلش شروع شود مثل `--prime /login` را به مسیرِ
  ویندوزی تبدیل می‌کند (مثلاً `D:/Program Files/Git/login`). یا `MSYS_NO_PATHCONV=1` را جلوی
  دستور بگذار، یا `--prime //login` بده، یا از PowerShell / `cmd` اجرا کن.
